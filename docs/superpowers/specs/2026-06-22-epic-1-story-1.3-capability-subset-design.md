# EPIC 1 · Story 1.3 — Reusable capability-set subset primitive (design)

**Date:** 2026-06-22
**Status:** Approved (brainstorm complete; awaiting implementation plan)
**Story:** vision-roadmap EPIC 1 · 1.3 — "Elevate `capability_override` +
`glob_subset` from per-package to repo-root ceiling."
**Constitution:** [ADR-0057](../../decisions/0057-root-allow-governance.md)
(decision 2: one capability vocabulary, one reused subset checker at every
lattice link).

## Purpose

Provide the single reusable subset relation that every lattice link in EPIC 1
calls: `capability_set_subset(child, parent)` over full `Capability` sets.
Today the subset logic is asymmetric and buried inside `compute_effective`
(it compares an *override* — kind-keyed `Vec<String>` allow-lists — against a
*package* `Vec<Capability>`). The root `[allow]` ceiling has `Vec<Capability>`
on both sides, so no existing function fits. This story builds and unit-tests
that primitive and refactors `compute_effective` onto its shared per-field
helpers (DRY). It adds **no enforcement** — 1.4 (`tau check`) and 1.5 (lattice
traversal) are the consumers.

## Scope boundary

**In scope (1.3):**

- A new `capability_set_subset(child: &[Capability], parent: &[Capability]) ->
  Result<(), CeilingViolation>` covering **every** `Capability` variant.
- A `CeilingViolation { kind, offender, reason }` error type.
- Extract shared per-field helpers (`paths_subset`, `string_set_subset`,
  `max_bytes_le`) and refactor `compute_effective` to call them — behavior
  unchanged, one implementation.
- Promote `glob_subset` from `pub(crate)` so the new module reuses it.
- Unit tests per variant + the regression guarantee that `compute_effective`'s
  existing tests stay green.

**Out of scope (deferred):**

- Any call from `tau check` → Story 1.4.
- Any lattice traversal across root/agent/spawn/tool → Story 1.5.
- The coarse-ceiling lint → Story 1.6.

## Placement

New module `crates/tau-pkg/src/capability_override/subset.rs`, declared in
`crates/tau-pkg/src/capability_override/mod.rs`. It exposes
`capability_set_subset`, `CeilingViolation`, and the extracted per-field
helpers. `glob_subset::is_glob_subset_set` / `is_glob_subset` change from
`pub(crate)` to crate-visible for `subset.rs` (kept `pub(crate)`; `subset.rs`
is in the same module tree). `capability_set_subset` and `CeilingViolation`
are `pub` (consumed by 1.4/1.5, and by `tau-cli`'s `tau check` which depends
on `tau-pkg`).

## The primitive

```rust
/// child ⊆ parent over full Capability sets, matched by kind.
/// Returns the first violation, or Ok(()) if every child cap fits under a
/// matching parent cap.
pub fn capability_set_subset(
    child: &[Capability],
    parent: &[Capability],
) -> Result<(), CeilingViolation>;

#[non_exhaustive]
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct CeilingViolation {
    /// Capability kind that violated (`"fs.read"`, `"net.http"`, `"agent.spawn"`, …).
    pub kind: String,
    /// The exact child entry that exceeded the ceiling (a path / host / command /
    /// allowed-kind / skill), or the kind name when the kind itself is unmatched.
    pub offender: String,
    /// Human-readable reason (e.g. "not a subset of any allowed path",
    /// "kind not in ceiling", "max_bytes 9000 exceeds 5000").
    pub reason: String,
}
```

`capability_set_subset` does NOT know about agents, links, or `[allow]`. The
caller (1.4/1.5) prepends framing such as `agent 'x': root ceiling violation:`.
First-offender: returns on the first child cap that fails.

### Kind matching

Each child cap is matched to a parent cap by kind identity (the same identity
`compute_effective` already uses: `Custom` by `name`, all others by their kind
discriminator). A child cap whose kind has **no matching parent cap** is a
violation with `reason: "kind not in ceiling"` — deny-by-default (a parent
ceiling of ∅ for that kind).

### Per-variant subset table

| kind | child ⊆ parent rule | offender on failure |
|---|---|---|
| `fs.read` / `fs.write` / `fs.exec` | child `paths` glob-⊆ parent `paths` (`paths_subset`) | the offending path |
| `fs.write` `max_bytes` | child `≤` parent (`max_bytes_le`; parent `None` = unlimited) | `"max_bytes=<child>"` |
| `net.http` | child `hosts` ⊆ parent `hosts` (`string_set_subset`); **`methods` not checked in 1.3** (matches today's `compute_effective`, which narrows hosts only) | the offending host |
| `process.spawn` | child `commands` ⊆ parent `commands` (`string_set_subset`) | the offending command |
| `agent.spawn` | child `allowed_kinds` ⊆ parent `allowed_kinds` (`string_set_subset`) | the offending kind |
| `skill.spawn` | child `allowed_skills` ⊆ parent `allowed_skills` (`string_set_subset`) | the offending skill |
| `task_list` | child `mode` ≤ parent `mode`, ordered `read ⊆ write ⊆ manage` | `"mode=<child>"` |
| `plan` | child `mode` ≤ parent `mode`, ordered `read ⊆ write` | `"mode=<child>"` |
| `Custom` | exact equality (`name` AND `params`); else violation | the custom `name` |

Notes:
- `net.http`: only `hosts` participate in the subset check, matching today's
  `compute_effective` (which narrows hosts and ignores `methods`). Bounding
  `methods` against the ceiling is a deliberate deferral — it would introduce a
  new semantic (and an "empty parent methods = ?" wildcard question) that the
  existing capability machinery does not have. A later story can add it once the
  ceiling vocabulary for methods is decided.
- `task_list` / `plan` mode ordering uses a fixed rank: `read=0, write=1,
  manage=2`; child rank `≤` parent rank. An unknown mode string on either side
  is a violation (`reason: "unknown mode"`).
- `Custom` is intentionally exact-match: ADR-0057 and `compute_effective` treat
  custom capabilities as not narrowable. A child `Custom` with no byte-identical
  parent `Custom` is a violation.

## The DRY refactor

Extract three pure helpers into `subset.rs`, each preserving today's exact
semantics:

```rust
pub(crate) fn paths_subset(child: &[String], parent: &[String]) -> Result<(), String>;     // = is_glob_subset_set
pub(crate) fn string_set_subset(child: &[String], parent: &[String]) -> Result<(), String>; // exact-set inclusion; returns first offender
pub(crate) fn max_bytes_le(child: u64, parent: Option<u64>) -> Result<(), String>;          // child ≤ parent; None = unlimited
```

`capability_override::compute_effective::validate_allow_subset` /
`validate_max_bytes` are refactored to call `string_set_subset` /
`max_bytes_le` (today they inline an exact-set loop and a `≤` check).
`paths_subset` is a thin alias over the existing `is_glob_subset_set`. No
behavior change — the existing `capability_override` tests are the regression
guard.

## Error handling

`CeilingViolation` is the only new error type. The per-field helpers return
`Result<(), String>` (the offending entry as the `String`);
`capability_set_subset` maps that into a `CeilingViolation` with the kind and a
reason. No change to `ProjectConfigError` or `OverrideExpandError` in this story.

## Testing (TDD)

Unit tests in `subset.rs`:

- One subset-OK + one offender-rejected per variant (fs.read/write/exec,
  net.http hosts, process.spawn, agent.spawn, skill.spawn, task_list, plan,
  Custom). One test asserting `net.http` `methods` differences do NOT cause a
  violation in 1.3 (locks the deferral).
- `fs.write` max_bytes: lower accepted, higher rejected, parent-`None`
  accepted.
- Deny-by-default: a child kind absent from parent → violation with
  `reason: "kind not in ceiling"`.
- `task_list`/`plan` mode ordering both directions (read⊆write OK,
  write⊆read rejected) + unknown-mode rejected.
- `Custom`: identical accepted, differing `params` rejected.
- `offender` field points at the exact violating entry (assert on it, not just
  that an error occurred).

Refactor regression: the entire existing `capability_override` test suite stays
green after the helper extraction (run it; no edits to those tests).

# EPIC 4.2 — control-flow interpreter (the recursive walk) — design

**Date:** 2026-07-18
**Status:** Proposed — pending review
**Epic:** 4 — IR control flow: structured blocks + dynamic regions  [needs 2]
**Story:** 4.2 (interpreter: recursive structured walk; bounded fork-join for Parallel;
resolve the nested-scope model 4.1 deferred).
**Anchors:** ADR-0058 (IR control-flow blocks — the data model this executes), ADR-0037
(workflow IR), ADR-0044 (`Locus`/`GoalPredicate`), ADR-0053 (`per_tool_call` checkpoint,
reused by Suspend in 4.3). New: ADR-0059 (interpreter semantics, this story).

## Problem & scope

EPIC 4.1 (PR #444) added four recursive structured-block variants to `tau-ir`'s `StepRun`
(`Branch`/`Parallel`/`Loop`/`Suspend`) plus a reusable `Condition`, bumped `ir_format` to
v2.4.0, and typechecked the blocks' *shape*. **4.1 shipped the blocks as inert data.** The
interpreter (`tau-runtime-core`) currently returns `RuntimeError::Internal("… lands in EPIC
4.2")` when the pipeline walk reaches any control-flow block — a loud stub, never a silent
skip.

4.1 also **explicitly deferred** one design hole (ADR-0058 §Consequences): how *nested* steps
inside a block scope their ids and outputs. 4.1's typecheck validates that nested steps
reference real nodes, but it *rejects* a `Loop.until` that reads its own body's output because
nested-scope visibility was not yet modeled.

**In scope (4.2):**
- The recursive interpreter walk that *executes* `Branch`, `Parallel`, and `Loop`.
- Resolve the nested-scope model (flat global namespace + execution-order visibility).
- Implement that model in the `tau-ir-lower` typecheck (uniqueness across the tree; the
  `Loop.until`-reads-body fix; parallel-branch isolation; nested-template ref-checking).
- Two named `RuntimeError` variants replacing the 4.1 generic stubs.
- ADR-0059.

**Out (later stories):** Suspend's checkpoint/resume round-trip (4.3 — 4.2 aborts loudly on
Suspend); `StepRun::Dynamic` capability-bounded regions (4.4–4.5); conformance / parallel
event-order normalization (4.6); lowering these blocks from `tau.toml` surface syntax (folds
into later usability work — 4.2 executes IR that already contains the blocks). **No
`ir_format` bump** — 4.2 changes the interpreter and the lowering typecheck only; the IR wire
format (v2.4.0) is unchanged.

## Decisions

### Decision 1 — nested scope: flat global namespace + execution-order visibility

Every `PipelineStepId` in the whole pipeline tree (top-level and nested) is **globally
unique**. There is **one flat `OutputStore`** keyed by bare id. The template grammar is
**unchanged** (`${steps.<id>.output}`; bare id everywhere). A reference (a `Condition`'s
`Locus::Output`, or a `${steps.<id>.output}` template ref) resolves iff the referenced step
**executed before** the reference point in the structured walk.

"Executed before" is *execution-order*, not pure lexical order, and differs per block:

| Reference site | In-scope steps |
|---|---|
| `Branch.on` | outer-earlier only (condition runs *before* `then`/`otherwise`) |
| `Branch.then`/`otherwise` step | outer-earlier + prior siblings in that arm |
| `Loop.until` | outer-earlier **+ the loop body's ids** (until runs *after* each body pass) |
| `Loop.body` step | outer-earlier + prior body ids (+ previous iteration's outputs at runtime) |
| `Parallel` branch step | outer-earlier + that branch's own prior steps **only** (never sibling branches — they are concurrent) |

A downstream step reads a block's result by **bare id** (`${steps.<inner>.output}`), because
the store is flat and block-transparent. In a `Loop`, a body step's output key is
**overwritten each iteration** (last-iteration-wins).

*Rejected alternatives:* hierarchical/pathed namespace (`${steps.<block>.<child>.output}`,
ids unique per-block) — changes the template grammar, the `Locus::Output` shape (an IR schema
bump), and the `OutputStore` keying, buying cross-block id reuse that hand-authored τ
workflows do not need. Block-encapsulated outputs (nested outputs invisible outside the
block) — dead-simple lexical rule, but makes loops/branches output-opaque so downstream steps
cannot consume their results without inventing a new "block export" IR feature. Flat-global is
the only option where "read a loop/branch result downstream" works with zero contract change.

### Decision 2 — `Parallel`: bounded cooperative fork-join (nginx model)

`tau-runtime-core` is `no_std` + `alloc` and **executor-agnostic** (only `futures-core`
traits; it cannot spawn tasks — the same code runs in the wasm guest and on embassy). So
`Parallel` concurrency is **cooperative multiplexing inside the single interpreter task**:
each branch fires its LLM/tool request and parks on `.await`; the driver polls the next
branch, firing *its* request. All requests are in flight at once, on one thread — the nginx
event-loop model, which is exactly right for τ's I/O-bound agent/tool branches.

- Each branch forks a **read-only `store.clone()`** (no `&mut` aliasing), runs via `run_steps`,
  and returns `(branch_index, produced_store)`.
- Branches are driven with `futures_util::stream::iter(futs).buffered(PARALLEL_CAP)` — a
  **bounded** number in flight (`PARALLEL_CAP = 8`, a hardcoded const for 4.2; "make it
  configurable" is a later story), and `buffered` **preserves result order** so the join is
  deterministic.
- At join, each branch's produced keys are **merged back into the shared store in branch-index
  order**. Because branches only *add* keys (Decision 1 isolates their reads to their own
  branch), the merge is a straight key insertion.
- Branch futures are polled in the same task → **no `Send` bound** is required between them.

Adds one dependency to `tau-runtime-core`: `futures-util = { default-features = false,
features = ["alloc"] }` (already transitively in `Cargo.lock`; keeps the crate `no_std`).

*Rejected alternatives:* sequential (concurrency = 1) — semantically correct but makes
`Parallel` pointless, since two 5s LLM waits take 10s instead of ~5s. True multi-thread
parallelism via a new `Spawn` port (apache prefork model) — delivers simultaneous *CPU*
across branches, but forces a new port + three host impls (tokio real, wasm/embassy no-op =
re-doing the cooperative path anyway) and a `Send + 'static` sweep through the whole
interpreter (`agent_loop`/`tool_dispatch`/`check`), for capacity I/O-bound agent workflows do
not use. If a future compute-heavy `Dynamic` region (4.4+) needs it, that is the right place
to introduce a `Spawn` port deliberately.

### Decision 3 — `Loop`: own bounded walk, hard exhaustion, feedback threading

**3a. Exhaustion is a hard error.** When `body` has run `max_iters` times and `until` never
held, the interpreter returns `RuntimeError::LoopExhausted { step, max_iters }` and the run
aborts. A loop that cannot reach its goal within its mandatory bound is a failure, not a
silent success — consistent with ADR-0058's "no runaway agents" and the no-silent-wrong-result
stance. (Rejected: stop-and-continue, which ships the last un-converged output and exits 0.)

**3b. `Loop` gets its own small bounded walk** and shares only the *primitives* with the
existing `Check` gate-rewind — condition evaluation (`eval_condition`, the existing
`evaluate_goal`, already reused by `Branch.on`) and the feedback-injection idiom. It does
**not** literally reuse the flat top-level gate-rewind index loop, whose flat-index arithmetic
(`gate_index`, `i = gate_idx`) would require projecting nested ids into the flat pipeline index
— fighting Decision 1's tree walk. A `Check` *inside* a loop body still rewinds within its own
body via the per-slice check logic in `run_steps` (see Component 1), so check-retry composes
without literal reuse.

**3b (feedback threads across iterations).** When iteration *N*'s `until` fails, its rationale
is carried into iteration *N+1*'s body as a prior agent turn (`"Previous attempt rejected:
<rationale>"`), reusing the existing `feedback: Option<String>` idiom (`pipeline.rs` +
`split_history` in `agent_loop`). A looping agent that is told *why* it is being asked again
converges faster; a blind re-roll is much weaker and more likely to exhaust.

### Decision 4 — `Suspend`: loud named error (round-trip deferred to 4.3)

The full HITL round-trip (checkpoint run state → emit event → wait for `resume_signal` →
seed-and-skip resume) is EPIC 4.3. In 4.2 the recursive walk reaching a `Suspend` (top-level
or nested) returns `RuntimeError::SuspendNotImplemented { step, resume_signal }` and aborts.
This keeps 4.1's never-silently-skip discipline while not shipping a half-built pause that
looks resumable but cannot resume. The only change vs today's generic `Internal` stub is a
**named** variant, giving 4.3 a clear seam. (Rejected: emit a `RunEvent::Suspended` +
`RunOutcome::Suspended` terminal now — introduces a public contract that looks resumable but
is a dead end until 4.3, which would then have to reshape it.)

## Architecture

### Component 1 — interpreter: extract a recursive `run_steps` (`tau-runtime-core`)

`run_pipeline` (`crates/tau-runtime-core/src/interpreter/pipeline.rs`) is today a flat
index-loop with inline `Check` gate-rewind. Refactor the step-execution core out into one
recursive function that both the top level and every nested body call:

```rust
async fn run_steps<D>(
    module: &Arc<IrModule>,
    steps: &[PipelineStep],
    input: &str,
    store: &mut OutputStore,
    dispatcher: &Arc<D>,
) -> Result<(), RuntimeError>
where D: ToolDispatcher + Send + Sync + 'static;
```

- `run_pipeline` becomes a thin wrapper: build the store, call `run_steps(&pipeline.steps, …)`,
  return the store.
- **Check gate-rewind stays per-slice.** The `gate_index`/`attempts`/`feedback` state is
  computed over the *current slice* of steps, so a `Check` inside a loop/branch body rewinds
  within its own body — the rewind machinery composes at any nesting depth with no flat-index
  projection.
- The leaf dispatch (Agent/Tool/Deterministic/Check) is behavior-preserving vs today.
- New block arms delegate to block executors (all `Box::pin`-recursed like the existing
  subflow/deliverable paths, since `run_steps` is self-recursive):
  - `run_branch` — `eval_condition(&on)`; run `then` or `otherwise` via `run_steps` on the
    shared `&mut store`.
  - `run_loop` — `for n in 1..=max_iters { run_steps(body, …); if eval_condition(until){return
    Ok} feedback = rationale }` then `Err(LoopExhausted)`; threads `feedback` into the body.
  - `run_parallel` — per branch fork `store.clone()`, `run_steps(branch, &mut snap)`, collect
    `(index, snap)`; `stream::iter(futs).buffered(8)`; merge each snapshot's keys back into
    `store` in index order.
  - `run_suspend` — `Err(SuspendNotImplemented)`.
- `eval_condition(&Condition, &store, reader, registry) -> CheckVerdict` lifts the existing
  `evaluate_goal(evaluates, predicate, …)` to take a `&Condition` (its `{ evaluates, predicate
  }`), keeping one code path for check-goal, branch, and loop conditions.

### Component 2 — `OutputStore` snapshot/merge for Parallel (`output_store.rs`)

Parallel branches must not alias `&mut store`. Each branch runs against `store.clone()` and its
produced keys merge back after join. Add a minimal helper — either a `merge(other:
OutputStore)` that inserts `other`'s keys, or a `delta(since: &BTreeSet<String>)` computing the
branch's new keys — sufficient to merge branch outputs in index order. Branches only add keys
(their reads are branch-isolated by Decision 1), so a straight insertion merge is correct. No
`OutputStore` schema change.

### Component 3 — typecheck: implement Decision 1's scope rules (`tau-ir-lower`)

Close two gaps in `crates/tau-ir-lower/src/lower/typecheck.rs` (`check_pipeline` /
`validate_step_run`):

1. **Global id uniqueness across the whole tree.** A pre-pass collects every nested
   `PipelineStepId`; a duplicate anywhere (nested or top-level) → `DuplicatePipelineStepId`.
   (Today only top-level ids are checked for uniqueness.)
2. **Execution-order visibility.** Replace the flat `seen_ids: &BTreeSet<&str>` with a scope
   that follows Decision 1's table:
   - `Loop.until` scope = outer-earlier **+ loop body ids** (the 4.1 fix — currently rejects
     body refs via `ConditionUnknownOutput`).
   - `Branch.on` scope = outer-earlier only (unchanged — already correct).
   - `Parallel` branch-step scope = outer-earlier **+ that branch's own prior steps** (never
     sibling branches).
   - **Nested step `input` templates are ref-checked** under the same scope. Today
     `extract_refs(&step.input)` runs only for top-level steps; nested-step inputs are
     unvalidated. 4.2 validates them (the "nested `${steps.<id>.output}` visibility" deferral).

### Error handling — two new named `RuntimeError` variants (`error.rs`)

```rust
/// A `Loop` ran `max_iters` iterations without its `until` condition holding.
LoopExhausted { step: String, max_iters: u64 },
/// A `Suspend` block was reached; HITL checkpoint/resume lands in EPIC 4.3.
SuspendNotImplemented { step: String, resume_signal: String },
```

Both replace the 4.1 generic `Internal("… lands in EPIC 4.2")` stubs and carry `thiserror`
boundary messages. `LoopExhausted` names the offending loop step and its bound;
`SuspendNotImplemented` names the step and the signal 4.3 will wait for.

## Testing

**`tau-ir-lower` (typecheck):**
- `Loop.until` reading its own body output now **accepts** (was rejected).
- `Branch.on` reading its own `then`-body output still **rejects** (`ConditionUnknownOutput`).
- `Parallel` branch-step referencing a *sibling* branch's step **rejects**.
- Duplicate nested `PipelineStepId` anywhere in the tree **rejects** (`DuplicatePipelineStepId`).
- A nested step `input` with a forward/unknown `${steps.<id>.output}` **rejects**.

**`tau-runtime-core` (interpreter, MockLlmBackend):**
- `Branch` picks the `then` arm when the condition holds, `otherwise` when it does not.
- `Loop` converges (breaks on `until`), **hard-errors** on exhaustion (`LoopExhausted`), and
  **threads feedback** (iteration 2's agent sees iteration 1's rejection rationale).
- `Parallel` runs both branches and merges both outputs, **index-ordered**; both branch
  outputs are present in the store after join.
- `Suspend` returns `SuspendNotImplemented`.
- **Option A end-to-end:** a downstream step reads a block's inner output by **bare id**.
- All existing `pipeline.rs` / `check.rs` tests stay green (the `run_steps` extraction is
  behavior-preserving on the flat path).

## DoD

`Branch`/`Parallel`/`Loop` execute via the recursive walk; `Parallel` is bounded cooperative
fork-join (`buffered(8)`, index-ordered merge); `Loop` hard-errors on exhaustion and threads
`until`-failure feedback; `Suspend` aborts with `SuspendNotImplemented`. The nested-scope model
(flat global + execution-order visibility) is enforced at typecheck: tree-wide id uniqueness,
`Loop.until`-reads-body accepted, parallel-branch isolation, nested-template ref-checking. Two
named `RuntimeError` variants replace the 4.1 stubs. ADR-0059 Accepted. No `ir_format` bump.
Existing flat-pipeline behavior unchanged. No Suspend round-trip (4.3), no Dynamic regions
(4.4), no conformance normalization (4.6).

## Risks

- **Refactoring the battle-tested `run_pipeline` gate-rewind into `run_steps`** risks regressing
  the flat Check-retry path. Mitigation: the extraction is behavior-preserving; all existing
  `pipeline.rs`/`check.rs` tests are the gate and must stay green with no assertion changes.
- **`futures-util` `no_std` build** — must use `default-features = false, features = ["alloc"]`;
  a stray std pull would break the wasm-interpreter/embassy builds. Mitigation: verify with an
  isolated `cargo check -p tau-runtime-core --no-default-features` (per the EPIC 0
  feature-graph-regression lesson).
- **`buffered` result ordering** — the deterministic merge relies on `buffered` (not
  `buffer_unordered`) preserving input order. Asserted by the index-ordered Parallel test.
- **Per-slice gate-rewind inside nested bodies** — a `Check` whose `gate` names a step outside
  its own slice would not resolve; this is already an `Internal` invariant-violation path today
  and stays one (typecheck can tighten gate-locality in a later story if needed).

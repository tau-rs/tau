# EPIC 1 · Story 1.5 — Enforce the relative lattice links (design)

**Date:** 2026-06-22
**Status:** Approved (brainstorm complete; awaiting implementation plan)
**Story:** vision-roadmap EPIC 1 · 1.5 — "Enforce the lattice: root ⊇ agent ⊇
dynamic-region ⊇ spawn ⊇ tool."
**Constitution:** [ADR-0057](../../decisions/0057-root-allow-governance.md)
(decision 4: every statically-decidable link enforced at build; the rest
runtime-bounded).
**Consumes:** 1.3 `capability_set_subset`; 1.4 `governance` category;
`tau_pkg::capability_override::compute_effective`.

## Purpose

1.4 enforced the "⊆ root" links (everything declared in `tau.toml` fits the
root ceiling) + closed-world references. 1.5 adds the **relative** lattice links
the constitution implies — the ones whose subset target is an *enclosing level*
rather than root — for every link that has a *static* representation today.

## Scope: which links, and why `agent ⊇ spawn` is deferred

```
L0  [tools.x].caps      ⊆  [allow.tools.x].ceiling     tool ⊆ its registered ceiling   (manifest-free)
L1  agent package caps  ⊆  [allow].ceiling             [allow] ⊇ package               (needs manifest)
L2  [tools.t].caps      ⊆  agent effective caps         agent ⊇ tool                    (needs manifest)
L3  subagent.caps       ⊆  agent.caps                   agent ⊇ spawn                   (DEFERRED — see below)
```

**`agent ⊇ spawn` (L3) has no build-time representation in tau today** and is
**deferred**. The runtime spawn path (`orchestration::virtual_tools::validate_agent_spawn`
/ `check_capability_subset`) shows: `agent.<kind>.spawn` carries a *free-string*
`kind`; `agent.spawn.allowed_kinds` lists kind strings with **no static
`kind → [agents.*]` mapping** (per-kind agent definitions are a documented
"v1.2 foundation" that does not exist); and the child's capabilities are supplied
**dynamically at spawn time**, then checked `child ⊆ parent` **at runtime**.
There is therefore nothing static to subset-check at build time. A build-time L3
would require first building per-kind agent definitions — a separate feature that
belongs with EPIC 4's dynamic-region work (same "caps chosen dynamically, bounded
by an envelope" shape ADR-0057 routes to EPIC 4). 1.5 records this and emits a
transparency `Note` (below); it does not fake a check.

**Out of scope (unchanged):** package-manifest *coverage* beyond the agent's own
package; the coarse-ceiling lint (1.6); dynamic-region links (EPIC 4).

## L1 semantics: package, not effective

L1 checks the agent's **package manifest caps ⊆ root** — the ADR's hard
`[allow] ⊇ package` link: a package that *requests* more than the constitution is
an error **even if an override would narrow it** (ADR-0057 decision 1 — "packages
are requests, capped at root"). This needs no override materialization (manifest
caps are already `Vec<Capability>`).

## L2 semantics: tool ⊆ the agent's effective caps

L2 checks each IR tool an agent references against the agent's **effective** caps
(manifest ∩ override) — a tool runs within the agent's *actual* grant. Effective
caps require materializing `compute_effective`'s output (below).

## Manifest resolution + materialization

New helper module `crates/tau-cli/src/cmd/check/agent_caps.rs`:

```rust
enum AgentCaps {
    Resolved { manifest: Vec<Capability>, effective: Vec<Capability> },
    NotInstalled,                          // → NeedsSetup; skip L1/L2 for this agent
    OverrideExpands(OverrideExpandError),  // → Error (override exceeds its package)
}

/// Resolve from the lockfile (ctx.scope) → the agent's package → its installed
/// manifest's declared capabilities; then compute_effective(manifest, overrides)
/// and materialize each EffectiveCapability into a concrete Capability.
fn resolve_agent_caps(agent: &AgentEntry, ctx: &CheckCtx) -> AgentCaps;
```

**Materialization** (the one new wrinkle): `compute_effective` yields
`EffectiveCapability { source, allow_override, deny, max_bytes_override }`.
Convert each to a `Capability` via the serde bridge — serialize `source`, replace
its list field (`paths`/`hosts`/`commands`) with `allow_override` minus `deny`
(when `allow_override` is `Some`), set `max_bytes` to `max_bytes_override` (when
`Some`), then `serde_json::from_value::<Capability>`. When all override fields are
absent, the materialized cap equals `source`.

## The checks (a `lattice` pass in `governance.rs`, only when `allow` present)

- **L0** — for each `(name, def)` in `project.tools` that has a matching
  `allow.tools.get(name)`: `capability_set_subset(&def.capabilities,
  &reg.ceiling)`. Err → `Error` rule `tau.governance.tool_exceeds_ceiling`:
  `tool '<name>': <kind> "<offender>" exceeds its [allow.tools.<name>] ceiling`.
- **L1 / L2** — per agent, `resolve_agent_caps`:
  - `NotInstalled` → one `NeedsSetup` rule `tau.governance.agent_caps_unresolved`
    (`agent '<id>' package '<pkg>' not installed — run \`tau resolve\` to check
    the lattice`); skip L1/L2 for this agent.
  - `OverrideExpands(e)` → `Error` rule `tau.governance.override_expands_package`.
  - `Resolved { manifest, effective }`:
    - **L1:** `capability_set_subset(&manifest, &allow.ceiling)` → Err → `Error`
      rule `tau.governance.package_exceeds_allow`: `agent '<id>' package
      capability <kind> "<offender>" exceeds [allow] ceiling`.
    - **L2:** for each `t` in `agent.tool_refs` where `project.tools` has `t`:
      `capability_set_subset(&project.tools[t].capabilities, &effective)` → Err →
      `Error` rule `tau.governance.tool_exceeds_agent`: `agent '<id>': tool '<t>'
      capability <kind> "<offender>" exceeds the agent's effective grant`.
- **L3 transparency** — if any agent declares an `agent.spawn` capability
  (in its effective/manifest caps), emit one `Note` rule
  `tau.governance.spawn_runtime_enforced`: "agent ⊇ spawn is enforced at runtime;
  build-time enforcement is deferred pending per-kind agent definitions
  (EPIC 4)." `Note` does not affect exit code. Omitted when no agent spawns.

## Finding shape

Same `CheckFinding` shape as 1.4 (`category: Governance`, `rule_id`, `summary`
naming the offender from `CeilingViolation`, `location`, `structured`). Findings
accumulate (all violations reported).

## Testing

- **L0** — unit tests in `governance.rs` from TOML fixtures (no manifest):
  tool caps within / exceeding its `[allow.tools]` ceiling.
- **Materialization** — unit tests on the `EffectiveCapability → Capability`
  helper (override narrows; deny subtracts; no-override passes through).
- **L1 / L2** — integration tests (`tests/cmd_check_lattice.rs`) with a fixture
  installed package (lockfile + on-disk manifest, mirroring `cmd_check_models.rs`):
  a package exceeding root → exit 2 with `package_exceeds_allow`; a tool
  exceeding the agent's effective grant → exit 2 with `tool_exceeds_agent`; a
  within-lattice project → clean; an uninstalled package → `NeedsSetup` (exit 3),
  not a false Error.
- **L3 Note** — unit test: a project with an `agent.spawn`-granting agent emits
  exactly one `Note`, exit 0 (no Error).

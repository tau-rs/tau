# EPIC 2.2 — publish the IR JSON Schema + conformance kit — design

**Date:** 2026-06-22
**Status:** Approved (brainstorm) — pending spec review
**Epic:** 2 — Lock the two contracts as public ABIs (constitutional; BLOCKS 3, 5; informs 4)
**Story:** 2.2 (publish the IR JSON Schema from `tau-ir` serde + a conformance kit)
**Anchors:** [ADR-0055](../../decisions/0055-tau-identity-two-contracts.md),
[ADR-0056](../../decisions/0056-contract-versioning-stability-surface.md),
[ADR-0051](../../decisions/0051-tau-ir-crate-split.md).

## Problem

ADR-0055/0056 fix the **authoring/IR schema** as one of tau's two public contracts,
versioned by the existing `tau-ir` `ir_format` field (currently `v2.3.0`). But the schema is
not *published* — frontend / SDK authors (EPIC 5's codegen, third-party authors) have no
machine-readable contract to validate generated IR against, and no conformance kit. ADR-0056's
"one source → no drift" principle requires the schema be **generated from the `tau-ir` serde
types**, not hand-maintained.

## Scope

**In:** generate + publish the JSON Schema for the IR as `tau-ir` serializes it today; a drift
test; a valid-IR conformance test; a conformance kit (schema + sample IR + README) for SDK
authors.

**Out (explicitly):**
- The root `[allow]` governance section — not in `tau-ir` today (EPIC 1 owns it in tau.toml /
  tau-pkg, PR #427). It enters this schema later as an **additive `ir_format` bump** once EPIC 1
  lowers `[allow]` into the IR. Decoupled here to avoid colliding with in-flight EPIC 1.
- SDK *codegen* from the schema — that is EPIC 5 / story 5.3.
- Side-by-side versioned schema artifacts (multiple `ir_format` versions published at once) —
  YAGNI until a second version exists; deferred to Phase δ distribution.

## Decision (Option A from brainstorm)

Generate the schema from the `tau-ir` serde types via `schemars` behind an opt-in `schema`
feature; commit one canonical file with the version embedded; gate correctness with a drift
test (schema == freshly-generated) and a valid-IR test (representative `IrModule`s validate
against the generated schema).

### 1. Generation (`tau-ir`)

- New optional dep `schemars` + a `schema` feature, defined simply as
  `schema = ["dep:schemars"]` (off by default; `schemars` is std and brings its own std, so
  the feature is a std-only path never enabled by `tau-runtime-core`'s no_std consumers — the
  no_std default build and the wasm guest are untouched).
- `#[cfg_attr(feature = "schema", derive(schemars::JsonSchema))]` on every type reachable from
  `IrModule` (the root): `IrModule`, `Workflow`, `Agent`, `Tool`, `ToolSpec`, `Deterministic`,
  `Node`, `ToolImpl`, `StepRun`, capability types, `IrFormatVersion`, etc.
- `#[cfg(feature = "schema")] pub fn ir_json_schema() -> serde_json::Value` — returns the
  generated schema for `IrModule`, with `$id` and `title` embedding
  `IrFormatVersion::current()` (e.g. `title: "tau IR (ir_format v2.3.0)"`).
- **schemars must reproduce the serde representation exactly** — particularly the tagged-enum
  encoding of `Node` / `ToolImpl` / `StepRun`. `schemars` honors serde attributes
  (`rename`/`tag`/`skip`/`untagged`); the valid-IR test (§3) is the proof.

### 2. Publish location + versioning

- One committed file: **`schema/ir/tau-ir.schema.json`** (repo root `schema/` tree). The
  `ir_format` version lives **inside** the file (`$id`/`title`), so consumers read a stable path
  and learn the version from the content. Versioned by `ir_format` per ADR-0056; git history is
  the version trail. No per-version filename (avoids churn; defer multi-version publishing).
- A reference page `docs/reference/ir-schema.md` (added to `docs/SUMMARY.md`) pointing SDK
  authors at the file + the kit.

### 3. Correctness gate (two tests)

- **Drift test** — `crates/tau-ir/tests/schema_drift.rs`, `#[cfg(feature = "schema")]`:
  asserts the committed `schema/ir/tau-ir.schema.json` byte-equals `ir_json_schema()` rendered
  with the canonical (sorted-key, pretty) JSON writer, AND that the embedded version equals
  `IrFormatVersion::current()`. `TAU_BLESS=1` re-writes the file (so the test is also the
  updater); the `xtask gen-ir-schema` subcommand is the ergonomic generation entry that sets
  this. Mirrors `crates/tau-mcp/tests/golden_canonical.rs`.
- **Valid-IR test** — a std test using the `jsonschema` crate (already a workspace dep):
  serialize representative `IrModule`s — chosen to exercise `Node`, `ToolImpl` (all 4 arms),
  and `StepRun` — and assert each **validates** against the generated schema. This is the
  load-bearing check: it fails if `schemars`' output diverges from the real serde encoding.
  Lives in a std crate (NOT `tau-ir`, to keep `jsonschema`/std out of it) — `tau-ir-lower`
  (std, depends on `tau-ir`) is the natural home: `crates/tau-ir-lower/tests/ir_schema_conformance.rs`.

### 4. Conformance kit

`schema/ir/` ships, committed:
- `tau-ir.schema.json` (the contract).
- `samples/*.json` — valid sample IR (agent+native-tool, agent+MCP-tool, deterministic-step,
  subflow) produced by serializing known `IrModule`s.
- `README.md` — "validate your generated IR against `tau-ir.schema.json`; e.g.
  `<jsonschema CLI / language snippet>`; the version is in the schema's `$id`."

The §3 valid-IR test validates exactly the shipped `samples/*.json` (the kit self-tests; the
"a sample IR validates" acceptance criterion).

### 5. `xtask` + CI

- `crates/xtask/`: a `GenIrSchema` clap subcommand (`cargo xtask gen-ir-schema`) that builds
  `tau-ir` with `--features schema`, renders `ir_json_schema()`, and writes
  `schema/ir/tau-ir.schema.json` (+ regenerates `samples/` from the canonical sample
  `IrModule`s so the kit can't drift from the types).
- CI: a step running `cargo test -p tau-ir --features schema` (drift) and the
  `tau-ir-lower` valid-IR test. Added to an existing linux job (e.g. `feature-flag-matrix`
  or `test-stable`), not a new workflow.

## File structure

| File | Responsibility |
|---|---|
| `crates/tau-ir/Cargo.toml` | `schemars` optional dep + `schema` feature |
| `crates/tau-ir/src/*.rs` | gated `JsonSchema` derives; `ir_json_schema()` |
| `crates/tau-ir/tests/schema_drift.rs` | committed-schema drift + version check |
| `crates/xtask/src/main.rs` | `gen-ir-schema` subcommand |
| `crates/tau-ir-lower/tests/ir_schema_conformance.rs` | jsonschema valid-IR + samples self-test |
| `schema/ir/tau-ir.schema.json` | the published contract (committed, generated) |
| `schema/ir/samples/*.json` | sample IR (committed, generated) |
| `schema/ir/README.md` | SDK-author conformance kit instructions |
| `docs/reference/ir-schema.md` + `docs/SUMMARY.md` | reference page |

## DoD

`cargo xtask gen-ir-schema` produces `schema/ir/tau-ir.schema.json` (version embedded);
the drift test pins it; the valid-IR test proves representative IR (all tagged-enum arms)
validates against it; the conformance kit (schema + samples + README) ships; a reference page
is in the book; a CI step runs both tests. No `[allow]`, no codegen, no std in `tau-ir`'s
default build.

## Risks

- **schemars ≠ serde encoding.** The whole contract is worthless if the generated schema
  rejects valid IR. Mitigation: the valid-IR test (§3) over all tagged-enum arms is the gate;
  if `schemars` mis-encodes a tagged enum, fix via `#[schemars(...)]` annotations to match serde,
  or (last resort) a targeted post-process in `ir_json_schema()` — documented if used.
- **schemars draft version.** schemars emits a specific JSON Schema draft; the `jsonschema`
  validator must be configured for the same draft. Pin both explicitly in the valid-IR test.
